# AWS 域名访问结果：受限迹象与其他失败原因

2026-09-28，依据原始请求日志、保存页面及已保存的robots响应做离线审计；没有重新访问候选网站或Google。统计单位为域名，每个域名归入一个主类别。

**本轮AWS新探测15,791个域名，其中939个（5.95%）有拒绝、认证、验证或限流迹象。这不是939个“因机房IP被封”的确诊记录。** 另299条为历史复用，来源时间和网络不完全相同，不能混入AWS出口归因。

## 受限迹象的明细

| 证据 | AWS域名数 | 请求阶段/说明 |
|---|---:|---|
| HTTP 403 | 859 | 702个发生在robots，157个发生在首页；仅证明该次请求被拒绝 |
| HTTP 401 | 34 | 31个robots、3个首页；认证限制，不等于IP封禁 |
| HTTP 429 | 7 | 全部发生在robots，已停止该站请求 |
| 保存内容显示验证/拒绝页面 | 39 | 原识别9个、后续完整标题规则补27个、此次robots HTML审计再补3个 |
| 合计 | 939 | 按域名去重，以上四项在本轮不重叠 |

首次重算得到936个；此次继续读取351份已保存的robots HTML，发现3个`Just a moment...`页面，才修正为939。还有3份正常标题页面嵌入了Cloudflare验证相关代码，**单有脚本不能证明页面访问被阻止**，没有计入939。其余未命中也不能据此保证不存在其他防护。

HTTP状态只描述响应行为，不能识别IP信誉或实际防护规则。[429的标准](https://www.rfc-editor.org/rfc/rfc6585#section-4)也不规定服务端怎样识别请求者、怎样累计请求。Google自身三次429与这些网站的访问结果需要分别看；当前没有做可隔离客户端、时间和出口因素的对照实验。

补充明细：

- DNS：1,141条“主机名没有可用地址”、672条“名称/服务未找到”、213条“暂时性解析失败”。仅表示当次解析结果，不能断言网站永远不存在。
- TLS：960条握手失败，418条证书验证失败。证书问题包含主机名不匹配186条、签发链无法验证119条、自签名68条、过期43条、链中自签名2条。不是全部“没有SSL证书”。
- 传输：911超时、249连接失败、32其他传输失败；握手、重置及超时有多种可能原因，不能排除部分涉及防护，但日志不能确定。
- robots：682条按规则不允许抓首页；698条包含当前解析器不支持的通配符/结束锚点规则；155份超过32KiB上限；44个要求比当前调度更慢的频率。后面三类主要是采集实现与调度限制，不是已证实IP封禁。
- 跳转：810条跳到apex/www之外或不支持的地址，89条降级HTTP，4条超限/缺目标，1条循环。重定向到别的公司主站也可能是有效网站，当前规则只是暂缓。
- 内容不足：2,889条带脚本且文本过少、106条薄/空页、633条首页达到128KiB上限、9条缺少关键词标签；“带脚本且文本少”不能证明一定需要JS，更不能证明垃圾站。
- 其他HTTP错误271条中243条为5xx，28条为其他4xx；部分是上游/站点异常，也可能存在防护，未凭状态码进一步猜测。

## 没拿到关键词，并不表示已看完首页后淘汰

15,791个域名中，**8,247个（52.2%）没有发出首页请求**：前置robots请求期间可能已发生DNS、TLS、网络、访问限制、跳转或robots规则问题。7,544个有首页请求记录。不是8,247个全被robots规则禁止，也不是全被IP屏蔽。

目前使用HTTPS-only、8秒传输超时、首页128KiB上限、不运行JavaScript、保守的robots解析器和仅apex/www跳转范围。它们节省请求和流量，但会使有效网站留在“证据不足”。此前“全部域名筛选完”仅表示每个域名都有一次判定记录，不表示每个首页都取得了内容。

## 当前证据的局限

原`probe_domains.fetch_public()`对HTTP错误返回状态码后，没有把已接收的错误正文写入结果，也只保留部分响应头。多数403/401/429没有可供复核的错误正文或完整防护头，所以无法可靠区分站点WAF、登录限制、机器人规则、地理限制或IP策略。这个限制此次已明确记录，不能补造过去的证据。

要缩小原因范围，应先改进robots解析、记录失败响应的受限大小正文与相关响应头，再对不同失败组做少量有边界的复核。当前没有因此启动重新抓取、扩大流量、调整IP或恢复Google查询。
